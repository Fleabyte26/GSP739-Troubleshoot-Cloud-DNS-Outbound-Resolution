# GSP739 - Troubleshoot a Cloud NAT gateway on the wrong subnet

Paste the blocks in order in Cloud Shell. Every block has the commands and ends with a check line, compare it with the note under the block.

## Known lab traps/bugs (read first)

1. Task 3 is built wrong on purpose (the NAT covers another-subnet, not the subnet of the VM). Click the Task 3 check BEFORE you run the Task 5 fix. If you fix it first, the Task 3 check has nothing wrong to find.
2. The VM has no external IP, so SSH goes through IAP. The blocks say so explicitly and need no key questions answered.
3. A failed ping in Tasks 2 and 4 is the expected result, not an error in your work.
4. After the fix in Task 5 the NAT needs up to a minute before the VM can reach the internet. The checker lags too: if a check fails, wait 30-60 seconds and click again.

## Setup

Edit the 2 quoted values first. They are the Region and Zone shown in the lab panel (also filled into the lab's own commands).

```bash
echo "REGION_FROM_LAB" > ~/region
echo "ZONE_FROM_LAB" > ~/zone
gcloud config get-value project > ~/project
gcloud config set compute/region `cat ~/region` --quiet
gcloud config set compute/zone `cat ~/zone` --quiet
head ~/project ~/region ~/zone
```

You should see your project ID, the region and the zone. The zone must start with the region name.

## Task 1. Create the VPC network and subnet

One network, two subnets (the VM will live in test-subnet), and a firewall rule that lets IAP reach port 22.

```bash
gcloud compute networks create test-vpc --subnet-mode=custom
gcloud compute networks subnets create test-subnet --network=test-vpc --region=`cat ~/region` --range=10.10.10.0/24
gcloud compute networks subnets create another-subnet --network=test-vpc --region=`cat ~/region` --range=10.20.20.0/24
gcloud compute firewall-rules create allow-iap-ssh --direction=INGRESS --priority=1000 \
  --network=test-vpc --action=ALLOW --rules=tcp:22 --source-ranges=35.235.240.0/20 --target-tags=iap-gce
gcloud compute networks subnets list --network=test-vpc --format='table(name,region.basename(),ipCidrRange)'
```

You should see test-subnet (10.10.10.0/24) and another-subnet (10.20.20.0/24) in your region.

## Task 2. Create the Compute Engine instance

A VM with no external IP. The ping proves it cannot reach the internet yet.

```bash
gcloud compute instances create test-instance --machine-type=e2-micro --subnet=test-subnet \
  --no-address --tags=iap-gce --zone=`cat ~/zone`
sleep 40
gcloud compute ssh test-instance --zone=`cat ~/zone` --tunnel-through-iap --quiet \
  --command="ping 8.8.8.8 -c 3 -W 2"
gcloud compute instances list --filter="name=test-instance" --format='value(name,status,networkInterfaces[0].networkIP)'
```

You should see the ping lose all 3 packets (100% packet loss, expected), then test-instance RUNNING with a 10.10.10.x address. If SSH says the connection failed, the VM was still booting: wait 30 seconds and paste the ssh line again.

Check my progress: Create a Compute Engine instance

## Task 3. Deploy the (wrong) Cloud NAT gateway

A static IP, a Cloud Router, and a NAT that only covers another-subnet. That is the colleague's mistake, copied on purpose.

```bash
gcloud compute addresses create nat-ip --region=`cat ~/region`
gcloud compute routers create test-nat-router --network=test-vpc --region=`cat ~/region`
gcloud compute routers nats create test-nat --router=test-nat-router --region=`cat ~/region` \
  --nat-external-ip-pool=nat-ip --nat-custom-subnet-ip-ranges=another-subnet
gcloud compute routers nats describe test-nat --router=test-nat-router --region=`cat ~/region` \
  --format='yaml(sourceSubnetworkIpRangesToNat,subnetworks)'
```

You should see LIST_OF_SUBNETWORKS and one subnetwork ending in another-subnet.

Check my progress: Create a Cloud NAT Gateway

STOP: do not go on to Task 5 until this check is green.

## Task 4. Troubleshoot network connectivity (no checkpoint)

Same ping, then compare where the NAT points with where the VM lives.

```bash
gcloud compute ssh test-instance --zone=`cat ~/zone` --tunnel-through-iap --quiet \
  --command="ping 8.8.8.8 -c 3 -W 2"
gcloud compute routers nats describe test-nat --router=test-nat-router --region=`cat ~/region` \
  --format='value(subnetworks[0].name.basename())'
gcloud compute instances list --filter="name=test-instance" \
  --format='value(networkInterfaces[0].subnetwork.basename())'
```

You should see the ping still fail, then two different names: another-subnet (what the NAT serves) and test-subnet (where the VM is). That mismatch is the root cause.

## Task 5. Fix the Cloud NAT subnet

Point the NAT at the subnet that actually hosts the VM.

```bash
gcloud compute routers nats update test-nat --router=test-nat-router --region=`cat ~/region` \
  --nat-custom-subnet-ip-ranges=test-subnet
gcloud compute routers nats describe test-nat --router=test-nat-router --region=`cat ~/region` \
  --format='value(subnetworks[0].name.basename())'
```

You should see test-subnet.

Check my progress: Fix the Cloud NAT Gateway

## Task 6. Test DNS resolution (no checkpoint)

```bash
sleep 45
gcloud compute ssh test-instance --zone=`cat ~/zone` --tunnel-through-iap --quiet \
  --command="ping 8.8.8.8 -c 3 -W 2; sudo apt-get install -y -q dnsutils > /dev/null; nslookup google.com"
```

You should see the ping succeed this time (0% packet loss) and nslookup print addresses for google.com. If the ping still fails, the NAT change has not landed yet: wait a minute and paste again.
